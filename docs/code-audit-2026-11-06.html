Rolling Mill Code Audit

6 Nov 2026 Commit 0bd6873 on main Backend (Fastify) + frontend (Next.js static export) About 35k lines of source

The code is tidy, but the numbers and the access model aren't safe to trust. Type-checks pass and all 191 backend unit tests pass, but those tests don't catch any of the 32 calculation bugs found. Several production, yield, energy and running-rate figures can be wrong on real data. The same is true of a shared-credential flaw that lets someone who was refused sign-in knock out the logbook for everyone.

Everything below was checked by reading the code, and most of it was proven with failing tests run against the real modules. All systems were mocked: no real historian, ERP or logbook was contacted, and nothing was written. Each finding is tagged Proven, Code read or Suspected.

Findings by severity

Fix these first

  1. Stop sharing one IOsense credential across all users.Keep the token per session, or use only the service PAT. Check the organisation before storing anything, and never let a failed request wipe the PAT. S-01 · S-07
  2. Fix the HSM counter maths.A day with no historian data gets another day's tonnes, and any small dip in the counter is treated as a reset, which counts the whole running total again. Both feed production, yield, running rate and plan. K-01 · K-02
  3. Pair numerator and denominator days in every ratio.Specific energy, mass yield, RMD running rate and HSM net production each divide totals taken over different sets of days. LSM also adds duplicate ERP vouchers together. K-04 – K-07 · K-09
  4. Close the Flux injection and lock down who can write.Escape ${, and refuse the catalogue request when the historian check fails. Set AUTH_ALLOWED_ORGANISATIONS, add a writer role, and refuse to start with auth off unless the environment is explicitly development. S-02 · S-03 · S-06
  5. Limit how much one request can cost.Put an upper bound on /api/hsm/stock, cap concurrent historian queries, and lower the rate limit on expensive routes. S-04 · S-05
  6. Make failures say they failed.The ERP sync reports success when four of its pulls failed, a logbook outage reads as "no plan saved", and a live-feed timeout never shows an error. K-08 · K-16 · K-23 · F-01
  7. Fix the CA-inputs month-switch race.It silently saves October's figures as November's. F-02

Done well

  • Every data route requires a signed session, and the enforcement is in one hook.
  • ERP SQL uses bound parameters, a read-only transaction and an offline sync. The API never opens Oracle.
  • Plant-day maths uses UTC plus a fixed IST offset, so it doesn't depend on the server's or the browser's time zone.
  • Trend queries are bucketed to about 500 points, divisions are guarded, and no NaN reaches the JSON.
  • The frontend keeps the session in sessionStorage, removes the SSO token from the URL, discards out-of-order responses, and cleans up its intervals.
  • Errors have one response shape with no stack traces, logs redact credentials, and the container runs as a non-root user.

Reproduce

Findings tagged Proven were reproduced with vitest tests that import the real modules, mock every external system (fetch, a fake InfluxDB HTTP server, synthetic ERP rows), and assert the correct behaviour, so they fail where the bug is.

Those tests were run from a temporary folder and aren't in the repo. The evidence line of each finding gives the inputs and outputs needed to rebuild one, for example as a regression test when the bug is fixed.
